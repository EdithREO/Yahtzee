# 服务器轨迹与网页播放

双击根目录 start_room_test.bat，两端打开启动窗口显示的局域网地址，A创建房间、B加入、A开始。等待两端骰盘加载完毕，A点击投骰；结束时两端应显示相同五颗点数。启动窗口按 Enter 停止服务器。

服务端 room/physics_world.gd 运行真实物理，默认20Hz采样。每次使用128位随机投掷ID，状态带递增seq、服务端单调时钟毫秒、五颗固定ID骰子的世界位置与四元数(x,y,z,w)。最终包带ended、点数和最终姿态，失败不伪造结果。可在启动前设置环境变量 YACHT_SAMPLE_HZ，限制5–60Hz。room/server.gd只接受已tests房间内当前玩家的roll请求（携带请求序号和回合号，不携带点数），按房间广播轨迹。刷新恢复时补发当前样本或终局；慢消费者发送缓冲失败时断开并恢复连接，避免无限积压。

客户端 room/trajectory_view.gd 复用原场景生成代码、骰子定义、材质和相机。骰子冻结、关闭碰撞及本地物理回调，只线性插值位置、slerp插值旋转。room/app.js 的 PLAYBACK_BUFFER_MS 默认150毫秒，可调整到100–200。根据ping/pong的最小RTT估计服务端时钟；按服务器时间播放，丢弃旧序号，跳过落后的样本，最后精确应用权威终态并检查朝上面。缓冲最多120包。客户端指标仅供诊断，不用于点数或结算。

新增独立 Web Trajectory 导出预设和 trajectory 主场景特性；网页文件在 room/viewer。project.godot 的普通主场景仍为原SinglePlayer场景。播放端使用单线程、无音频HTML壳，局域网HTTP实测能运行，没有修改浏览器安全设置。保持同源 /ws。未使用公网隧道。

性能显示与本次证据：
- 同机两个独立浏览器标签页，通过192.168.1.3的网页入口tests两轮投掷、双方终态一致；第二轮终点6/6/3/6/3，seq45，位置完全相同、旋转分量差约1e-12、朝上面核对均0错误。B刷新恢复同一终态。
- 浏览器requestAnimationFrame采样：两端约165FPS，帧时间均值6.07ms、P95 6.20ms（短时样本，非持续负载基准）。
- 第二轮：A请求到Godot应用首个轨迹约253ms，B收到开始到应用轨迹154ms；不含显示器扫描延迟。
- 第二轮服务器物理帧均值0.679ms，最大0.815ms；这是Godot全进程TIME_PHYSICS_PROCESS指标，包含上一物理帧，不是独立房间CPU计时。首轮均值0.624ms、最大1.141ms。
- 第二轮双端播放时间差估计3.2ms，RTT误差参考±6.5ms；为软件时钟估计，不是两台显示器实际画面同步测量。
- 第二轮轨迹状态JSON双端累计79.7KiB；首轮116.0KiB。计数不包含WebSocket/TCP帧头、开始/最终包及诊断消息，也不包含初次加载Godot资源。

仍需真实Wi-Fi两台设备复测：同一网络打开地址，按上述流程投掷，观察两端数据、断开Wi-Fi并在两分钟内恢复原标签页。当前没有可控制的第二台电脑或手机，本次不能声称跨设备通过。未模拟高丢包/长延迟、多房间负载。未接入完整回合、保留骰子或结算；原Windows EXE与SinglePlayerWebpublic目录保持原版本。

重新导出需使用4.7.2模板和 Web Trajectory 预设。服务端逐次物理结果日志仍保存在 user://physics_logs，服务端控制台输出ROLL_METRICS。日志不包含会话令牌。开发tools注入的MutationObserver控制台异常曾出现；未观察到Godot播放脚本报错或该异常阻断运行。
